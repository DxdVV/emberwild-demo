# Технический и визуальный подход к проекту

## 1. Общая цель

Игра должна разрабатываться как полноценный коммерческий инди-проект высокого качества, а не как прототип, game jam, учебный проект или демонстрация механики.

Главные приоритеты:

1. Высокое визуальное качество.
2. Богатый современный pixel-art.
3. Чистая и расширяемая архитектура.
4. Предсказуемое поведение игры.
5. Хорошая производительность.
6. Удобство дальнейшей разработки.
7. Минимум технического долга.
8. Возможность безболезненно добавлять новые игровые системы, контент, эффекты и локации.

Если существует быстрый "хак" и чуть более долгий архитектурно правильный вариант — по умолчанию выбирать правильный вариант.

Не оптимизировать разработку под "лишь бы заработало".

---

# 2. Движок

Основной движок: Godot 4.x, актуальная стабильная версия.

Основной язык: GDScript.

Использовать нативные возможности Godot там, где они подходят:

- Scene/Node architecture
- Resources
- signals
- AnimationPlayer
- AnimationTree
- TileMap/TileMapLayer
- CanvasLayer
- SubViewport
- shaders
- GPUParticles2D
- Light2D
- navigation
- аудиосистему Godot
- input actions

Не изобретать собственные аналоги встроенных систем без объективной причины.

При этом не строить всю архитектуру игры вокруг конкретной сцены или конкретного уровня.

---

# 3. Визуальная цель

Это НЕ минималистичный ретро-pixel-art.

Целевая эстетика:

"modern high-detail pixel art inspired by 16/32-bit games"

Pixel-art должен быть:

- детализированным;
- богатым по цвету;
- атмосферным;
- многослойным;
- с хорошо читаемыми силуэтами;
- с выразительным освещением;
- с большим количеством деталей окружения;
- с современной динамикой сцены;
- с аккуратными визуальными эффектами.

Не ограничивать искусственно палитру количеством цветов старых консолей.

Допускается большая палитра цветов и оттенков.

Старые консоли являются визуальным вдохновением, а не техническим ограничением.

Игра должна выглядеть как современная интерпретация дорогой 2D pixel-art игры, а не как буквальная эмуляция Mega Drive/SNES.

---

# 4. Базовое разрешение

Ориентироваться на внутреннее игровое разрешение:

640x360

Если конкретный тест покажет, что другое разрешение лучше соответствует масштабу графики, можно предложить изменение, но не менять его без аргументации.

640x360 должно рассматриваться как базовая координатная система визуального рендера.

Целевые разрешения экранов:

1280x720   = x2
1920x1080  = x3
2560x1440  = x4
3840x2160  = x6

При масштабировании необходимо сохранять четкость pixel-art.

Не допускать:

- случайного размытия спрайтов;
- дробного масштабирования pixel-art без необходимости;
- shimmering;
- crawling pixels;
- дрожания камеры относительно pixel grid;
- неравномерной толщины пикселей.

Все текстуры pixel-art должны использовать корректные filtering/import settings.

По умолчанию:
- nearest filtering;
- без нежелательного mipmapping для pixel-art;
- корректная pixel snapping стратегия.

При этом UI можно рендерить отдельно в более высоком разрешении, если это улучшает читаемость.

---

# 5. Масштаб ассетов

Не использовать чрезмерно мелкие персонажи уровня старых 8/16-bit игр, если этого не требует дизайн.

Главные персонажи могут иметь размер порядка 80-120 пикселей по высоте в базовом разрешении.

Это должно позволять отображать:

- лицо;
- волосы;
- одежду;
- ремни;
- оружие;
- броню;
- мелкие предметы;
- выразительную анимацию.

Окружение должно соответствовать этому уровню детализации.

Не использовать огромный персонаж на фоне примитивных тайлов.

Качество ассетов должно быть визуально согласованным.

---

# 6. Построение сцены

Локации не должны выглядеть как один плоский TileMap.

Использовать многослойную композицию.

Пример архитектуры визуальной сцены:

World
  Background
    Sky
    Clouds
    FarEnvironment
    Mountains
    DistantArchitecture

  ParallaxBack
    Trees
    Buildings
    Terrain

  Gameplay
    Ground
    Props
    Characters
    Enemies
    InteractiveObjects

  ParallaxFront
    Vegetation
    ForegroundProps
    Silhouettes

  Atmosphere
    Fog
    Dust
    Rain
    Snow
    Smoke
    Embers
    SmallParticles

  Lighting
    GlobalLight
    LocalLights
    DynamicLights

  PostFX

Это только пример структуры, а не обязательные названия узлов.

Главная идея:
сцена должна иметь визуальную глубину.

---

# 7. Parallax и глубина

Использовать несколько уровней параллакса там, где это визуально оправдано.

В крупной сцене может быть 5-10 визуальных глубин.

Например:

- очень дальний фон;
- дальняя архитектура;
- средний фон;
- дальняя растительность;
- игровой слой;
- ближняя растительность;
- foreground элементы.

Разные слои могут иметь:

- разную скорость движения;
- различную насыщенность;
- различную яркость;
- атмосферную перспективу;
- разные эффекты тумана.

Не делать параллакс просто ради движения.

Он должен усиливать ощущение пространства.

---

# 8. Освещение

Pixel-art не означает отказ от современного освещения.

Использовать динамическое освещение аккуратно и художественно.

Поддерживать:

- ambient lighting;
- локальные источники света;
- костры;
- лампы;
- свечи;
- окна;
- неон;
- вспышки;
- выстрелы;
- магические эффекты;
- динамические источники света.

Свет должен взаимодействовать с общей цветовой композицией сцены.

Не превращать pixel-art в гладкую 3D-картинку.

Эффекты должны сохранять pixel-art эстетику.

Если используются normal maps для некоторых ассетов, делать это осторожно.

Normal maps должны усиливать форму, а не создавать впечатление пластикового 3D.

---

# 9. Атмосферные эффекты

Активно использовать небольшие динамические детали, чтобы мир не выглядел статичной картинкой.

Примеры:

- пыль;
- дым;
- туман;
- искры;
- падающая листва;
- снег;
- дождь;
- насекомые;
- пепел;
- пар;
- летающий мусор;
- мелкие частицы;
- брызги воды;
- следы от движения.

Для большого количества простых частиц использовать GPUParticles2D.

Количество эффектов должно масштабироваться в зависимости от производительности.

Создать графические настройки для уменьшения количества вторичных эффектов на слабом железе.

---

# 10. Шейдеры

Шейдеры являются частью художественного инструментария проекта.

Можно использовать shader effects для:

- воды;
- дыма;
- тумана;
- ветра;
- травы;
- листвы;
- heat distortion;
- dissolve;
- damage effects;
- screen transitions;
- цветокоррекции;
- локальных атмосферных эффектов;
- отражений;
- волн;
- свечения.

Не использовать шейдеры ради технической демонстрации.

Каждый shader должен решать конкретную художественную или игровую задачу.

Обязательно учитывать производительность.

---

# 11. Цветокоррекция

Разные локации должны иметь собственную визуальную идентичность.

Использовать:

- palette direction;
- environment tint;
- lighting temperature;
- fog color;
- contrast;
- saturation;
- локальные эффекты.

Например:
холодная локация не должна отличаться от теплой только заменой фона.

Вся сцена должна иметь согласованный цветовой язык.

---

# 12. Анимация

Не ограничиваться только минимальными idle/run/attack анимациями.

Персонажи должны ощущаться живыми.

Где это оправдано, предусматривать:

- idle variations;
- anticipation;
- recovery;
- secondary motion;
- breathing;
- hair movement;
- clothing movement;
- weapon movement;
- hit reactions;
- environmental reactions;
- transitions между состояниями.

Анимации должны иметь правильный timing.

Не делать мгновенные переходы там, где они визуально выглядят дешево.

Gameplay responsiveness при этом важнее реалистичности.

Если необходимо, визуальная анимация может отделяться от физического/gameplay состояния.

---

# 13. Камера

Камера является отдельной системой.

Не писать управление камерой внутри Player.

Предусмотреть CameraController.

Он должен потенциально поддерживать:

- follow;
- smoothing;
- dead zones;
- look ahead;
- camera bounds;
- camera zones;
- zoom;
- scripted movement;
- shake;
- impulses;
- cinematic transitions.

Camera shake должен использоваться через централизованную систему.

Разные эффекты должны суммироваться корректно, а не напрямую перезаписывать position камеры.

---

# 14. Архитектура

Не строить гигантские скрипты на несколько тысяч строк.

Использовать композицию.

Предпочитать небольшие специализированные компоненты.

Например:

Character
  MovementComponent
  HealthComponent
  HitboxComponent
  HurtboxComponent
  AnimationController
  StateMachine
  AudioEmitter
  EffectsController

Это концептуальный пример.

Не нужно буквально создавать компонент для каждой переменной.

Избегать как монолитов, так и бессмысленной чрезмерной абстракции.

---

# 15. State machines

Для сложного поведения использовать явные состояния.

Например:

Idle
Move
Jump
Fall
Attack
Hurt
Dead

или для AI:

Idle
Patrol
Investigate
Alert
Chase
Attack
Search
Return

Не строить сложное поведение на сотнях вложенных if.

Состояния должны иметь ясные:

enter()
exit()
update()
physics_update()

или аналогичную структуру.

---

# 16. Data-driven design

Игровые параметры не должны быть хаотично захардкожены в скриптах.

Использовать Godot Resources для конфигурации:

- персонажей;
- оружия;
- врагов;
- способностей;
- предметов;
- эффектов;
- настроек окружения;
- уровней сложности;
- визуальных профилей.

Код описывает поведение.

Resources описывают данные.

По возможности новые варианты контента должны создаваться изменением данных, а не копированием кода.

---

# 17. Сигналы и зависимости

Системы должны иметь минимальные прямые зависимости друг от друга.

Использовать signals для событий, когда это разумно.

Например:

health_changed
died
damage_received
item_collected
state_changed

Не использовать глобальный EventBus для абсолютно каждого события.

Глобальные системы должны быть ограничены действительно глобальными задачами.

---

# 18. Autoload

Не превращать Autoload в свалку.

Autoload допустим для систем вроде:

- GameManager;
- SaveManager;
- AudioManager;
- SceneManager;
- SettingsManager;
- возможно EventBus.

Но только если система действительно глобальная.

Не складывать туда gameplay logic конкретных уровней.

---

# 19. Физика

Gameplay physics должна быть детерминированной настолько, насколько это возможно в рамках Godot.

Использовать _physics_process для физически значимого поведения.

Не привязывать скорость игры к FPS.

Все скорости должны учитывать delta там, где это необходимо.

Коллизии должны иметь понятные layers/masks.

Документировать назначение collision layers.

---

# 20. Hitbox / Hurtbox

Если в игре есть боевые взаимодействия, использовать отдельную систему hitbox/hurtbox вместо проверки столкновений основного тела персонажа.

Это позволит отдельно контролировать:

- физическое тело;
- зону получения урона;
- зону нанесения урона;
- взаимодействия;
- invulnerability frames.

Не смешивать все типы столкновений в одну CollisionShape.

---

# 21. Визуальный отклик

Каждое важное действие должно иметь feedback.

Использовать комбинации:

- animation;
- sound;
- particle;
- camera impulse;
- light flash;
- shader;
- hit stop;
- screen feedback.

Но избегать визуального шума.

Цель:
игрок должен физически ощущать действие через картинку и звук.

---

# 22. Audio architecture

Не размещать звук хаотично в игровых скриптах.

Создать понятную аудиоархитектуру.

Разделять:

- Music
- SFX
- UI
- Ambience
- Voice

Использовать Audio Bus.

Предусмотреть:

- volume settings;
- mute;
- ducking;
- positional audio;
- random pitch variation;
- random sample variation.

Повторяющиеся звуки не должны звучать как один и тот же WAV-файл каждый раз.

---

# 23. UI

UI должен быть архитектурно отделен от игрового мира.

UI не должен зависеть от конкретных экземпляров сцены, если это можно избежать.

Предусмотреть корректное масштабирование.

Не обязательно рендерить UI в 640x360.

Интерфейс может иметь более высокое разрешение для хорошей читаемости текста.

Стилистически UI должен соответствовать pixel-art игре, но текст не должен страдать ради эстетики.

---

# 24. Сохранения

С самого начала предусмотреть нормальную архитектуру save system.

Не сериализовать случайным образом всю SceneTree.

Сохранять только необходимые данные.

Save format должен иметь version.

Например:

save_version
player
world
progression
settings

Предусмотреть возможность миграции старых сохранений после изменения структуры данных.

---

# 25. Scene transitions

Переходы между сценами должны идти через SceneManager или аналогичную систему.

Не делать get_tree().change_scene_to_file() хаотично из разных объектов.

При необходимости поддерживать:

- loading screen;
- fade;
- async loading;
- progress indication;
- persistent data.

---

# 26. Object lifecycle

Следить за созданием и уничтожением объектов.

Для часто создаваемых объектов при необходимости использовать pooling:

- projectiles;
- particles;
- decals;
- floating text;
- effects.

Не использовать pooling автоматически для всего.

Сначала профилировать.

---

# 27. Производительность

Не заниматься преждевременной микрооптимизацией.

Но архитектура не должна изначально создавать очевидные проблемы производительности.

Особое внимание:

- количеству draw calls;
- количеству CanvasItem;
- частицам;
- shader complexity;
- большому количеству _process;
- физическим объектам;
- navigation;
- динамическому освещению.

Для объектов, которым не нужен каждый кадр, не использовать постоянный _process.

Профилировать через инструменты Godot.

Оптимизировать на основании измерений.

---

# 28. Debug tools

Разработка должна иметь debug layer.

Предусмотреть возможность отображать:

- collision shapes;
- hitboxes;
- hurtboxes;
- AI states;
- navigation;
- paths;
- velocities;
- spawn points;
- triggers;
- camera zones.

Debug visualization не должна попадать в production интерфейс.

Также желательно сделать developer/debug menu.

---

# 29. Логирование

Использовать осмысленные сообщения об ошибках.

Не оставлять сотни print().

Критические ошибки должны содержать контекст:

- имя объекта;
- тип объекта;
- сцена;
- ожидаемое состояние.

Не подавлять ошибки молча.

---

# 30. Структура проекта

Поддерживать понятную структуру директорий.

Например:

res://
  assets/
    characters/
    environments/
    props/
    effects/
    ui/
    audio/

  scenes/
    characters/
    enemies/
    levels/
    ui/
    effects/

  scripts/
    components/
    systems/
    states/
    utilities/

  resources/
    characters/
    enemies/
    items/
    weapons/
    environments/

  shaders/

  autoload/

  debug/

Не создавать десятки файлов в корне проекта.

Структуру можно корректировать по мере роста проекта.

---

# 31. Именование

Использовать единый стиль именования.

GDScript:
snake_case для переменных и функций.
PascalCase для class_name.

Имена должны объяснять назначение.

Плохие имена:
manager2
temp
thing
obj
data2
fix

Хорошие имена должны позволять понять назначение кода без изучения реализации.

---

# 32. Комментарии

Не писать комментарии, объясняющие очевидный синтаксис.

Плохой комментарий:

# increase health
health += 10

Комментарии должны объяснять WHY, а не WHAT.

Документировать:

- необычные архитектурные решения;
- математические алгоритмы;
- ограничения;
- обходные решения;
- причины странного поведения.

---

# 33. Не дублировать код

Если одинаковая логика начинает появляться в нескольких местах, рассмотреть выделение общего компонента или функции.

Но не создавать абстракцию после первого повторения.

Абстракция должна решать реальную повторяющуюся задачу.

---

# 34. Ошибки и edge cases

Не реализовывать только happy path.

Для каждой системы учитывать:

- отсутствующие ссылки;
- уничтоженные объекты;
- неправильные данные;
- пустые списки;
- быстрые повторные действия;
- смену сцены;
- pause;
- restart;
- смерть объекта;
- одновременные события.

Если потенциальный edge case очевиден, обработать его сразу.

---

# 35. Тестируемость

Критически важные игровые системы проектировать так, чтобы их можно было тестировать независимо.

Особенно:

- damage;
- health;
- inventory;
- state machines;
- save/load;
- calculations;
- progression.

Не обязательно писать unit test для каждой мелочи.

Но фундаментальные системы должны иметь автоматизированные проверки.

---

# 36. Git

Работать небольшими логическими изменениями.

Перед крупным рефакторингом оценивать затрагиваемые системы.

Не смешивать в одном изменении:

- огромный рефакторинг;
- новую механику;
- визуальную переделку;
- исправление случайных багов.

Изменения должны быть обозримыми.

---

# 37. Работа с существующим кодом

Перед изменением существующей системы сначала разобраться:

- как она устроена;
- кто ее использует;
- какие зависимости существуют;
- что может сломаться.

Не переписывать работающие системы просто потому, что другой вариант кажется красивее.

Рефакторинг должен иметь причину.

---

# 38. При реализации новой функции

Перед написанием значимого функционала:

1. Посмотреть существующую архитектуру проекта.
2. Найти связанные системы.
3. Определить, куда функциональность логически должна относиться.
4. Не дублировать уже существующий механизм.
5. Реализовать минимально достаточную архитектуру.
6. Проверить типичные edge cases.
7. Запустить проект.
8. Проверить ошибки Godot.
9. Проверить визуальное/игровое поведение.
10. После этого считать задачу выполненной.

"Код компилируется" не означает "задача выполнена".

---

# 39. При обнаружении проблемы

Не маскировать симптом, если можно устранить первопричину.

Перед фиксом понять:

- почему это происходит;
- где возникло неправильное состояние;
- является ли ошибка локальной или архитектурной.

Предпочитать исправление причины вместо набора дополнительных if.

---

# 40. Временные решения

Если по объективной причине используется временное решение, явно обозначить его:

TODO:
что именно временно,
почему,
какое правильное решение должно быть впоследствии.

Не оставлять скрытые костыли.

---

# 41. Placeholder assets

Допускается использовать placeholder графику на ранних этапах.

Но архитектура не должна быть привязана к размерам и свойствам placeholder-ассетов.

Когда появляется финальная графика, ее подключение не должно требовать переписывания gameplay systems.

---

# 42. Визуальные эффекты и gameplay

Разделять:

GAMEPLAY STATE
и
VISUAL PRESENTATION.

Например попадание может сначала регистрироваться игровой системой, а затем визуальная система получает событие и воспроизводит:

- анимацию;
- звук;
- частицы;
- вспышку;
- camera shake.

Не делать так, чтобы gameplay зависел от существования визуального эффекта.

---

# 43. Quality bar

Каждый новый элемент оценивается не только по критерию:

"работает ли он?"

Но и:

- хорошо ли он интегрирован;
- понятен ли код;
- можно ли его расширять;
- не ломает ли он существующую архитектуру;
- имеет ли действие достаточный feedback;
- выглядит ли оно завершенным;
- нет ли очевидных edge cases;
- соответствует ли оно визуальному стилю.

Нельзя считать задачу завершенной только потому, что базовая функция появилась.

---

# 44. Vertical slice

На раннем этапе разработки предпочтительно создать небольшой, но максимально качественный vertical slice.

Лучше:

одна маленькая локация,
один законченный персонаж,
несколько взаимодействий,
освещение,
частицы,
звук,
UI,
анимации,
эффекты

в почти финальном качестве,

чем десять огромных пустых уровней с временной реализацией.

Vertical slice должен определить реальный quality bar всего проекта.

---

# 45. Производство контента

Архитектура должна облегчать производство большого количества контента.

Новые:

- враги;
- NPC;
- предметы;
- эффекты;
- локации;

по возможности должны собираться из существующих систем и данных.

Не создавать отдельную программную архитектуру для каждого нового объекта.

---

# 46. Инструменты редактора

Если какая-либо операция будет регулярно повторяться вручную, рассмотреть создание editor tool.

Например:

- размещение объектов;
- генерация variation;
- настройка зон;
- preview данных;
- spawn editor;
- environment profiles.

Использовать @tool там, где это реально ускоряет разработку.

Проект должен становиться удобнее разрабатывать по мере его роста.

---

# 47. Главное правило визуальной разработки

Pixel-art ассет является базой, но финальный кадр создается системой.

Финальный кадр =

pixel-art
+ композиция
+ layering
+ parallax
+ animation
+ lighting
+ particles
+ atmosphere
+ shaders
+ sound
+ camera
+ feedback.

Не пытаться получить весь визуальный результат одним огромным статичным изображением.

Мир должен ощущаться живым.

---

# 48. Главное правило инженерной разработки

Не делай код только для сегодняшней задачи.

Но и не проектируй гипотетический универсальный игровой движок.

Создавай самый простой вариант архитектуры, который:

- качественно решает текущую задачу;
- имеет ясные границы ответственности;
- допускает вероятное расширение;
- не создает очевидного технического долга.

---

# 49. Если есть несколько вариантов реализации

При значимых архитектурных решениях сначала кратко сообщай:

- какие есть варианты;
- какой предлагаешь;
- почему;
- какие компромиссы.

После этого реализуй выбранный вариант.

Для мелких очевидных решений согласование не требуется.

---

# 50. Общий стандарт

Ориентир по мышлению:

это проект, который потенциально должен выйти в Steam и который спустя несколько лет разработки должен оставаться поддерживаемым.

Не относись к нему как к временному AI-generated прототипу.

Codex должен выступать не только как генератор кода, но и как опытный технический разработчик проекта:

- следить за архитектурой;
- замечать потенциальный технический долг;
- предлагать рефакторинг, когда он действительно нужен;
- сохранять согласованность систем;
- учитывать производительность;
- учитывать production workflow;
- проверять результат своей работы.

Любое решение должно оцениваться в контексте всего проекта, а не только текущего запроса.
